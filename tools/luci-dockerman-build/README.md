# Dockerman normal dependency package candidate

This candidate builds only the selected `luci-app-dockerman` package with ordinary OpenWrt dependency traversal. It pins OpenWrt `4e9642517b48bae612ff10fb72fb9199e559500e`, LuCI `cb87fe60e1e2e052af36a93647f2264577829e0a`, and packages feed `07e0d16305d2b5903b37ad7913e33e18795f81a4`. Before compilation the runner regenerates and checks the reviewed Dockerman-only metadata expectations, using run `45780167961`, artifact `15097324501`, config SHA-256 `4678b8d328391f97ba85b19020cbdcc077cccc528dc79553b99625627f25ae17`, and Dockerman-plus-kernel selected-scope graph SHA-256 `dbd149322c47f4ee8e75aa8cc3a8e0caf51b5c425561866fe26da8fdaced2ddc` (2,165 original-order rows). Full raw `.packagedeps` is retained and pinned for equality within each run; unrelated global spelling/order variants are not treated as Dockerman-scope changes.

The `source-oracle.json` emitted and pinned by the existing metadata probe covers 67 Dockerman source rows. The selected main-package projection is 22 unique files: 13 JavaScript files, four SVG files, two JSON files and three Ucode files. Its root RPC provider `usr/share/rpcd/ucode/docker_rpc.uc` projects as mode 0755; the other 21 files project as 0644. With the exact pinned config's JS/CSS minifiers disabled, all 22 projected members must be source-equal. No `.htm`/`.ut` substitution, app `src/` compilation, or package-owned shell member is expected. Translation catalogs and resulting `luci-i18n-*` packages remain separate. The `luci-app-dockerman` IPK must have control `Version: 26.134.50559~d5129a1`, `Architecture: all`, and exactly those 22 regular data files. Extra files, missing files, path aliases and special entries fail the comparison.

The comparator verifies pinned Git blob and mode, the expected package preparation copy, the full stage, strict IPK data/control archives, and exact file bytes and modes. It retains the selected prepared copies, complete stage including `CONTROL`, the raw app IPK and receipts in the run-owned output. Companion IPKs are identified by parsing their outer and control archives only: Compose intentionally has a data symlink, so its contents are not passed through the selected app's strict regular-file parser. The run records the observed IPK filename/hash/size inventory across the four scanned x86_64 Luci, packages, base and target repositories, then requires the direct and cycle-critical provider controls: luci-base, Docker CLI, dockerd, Docker Compose, ttyd, containerd, runc, tini, ucode-mod-socket, kernel and the five config-selected kmods. The virtual kernel package carries `6.12.116~<vermagic>-r1`; the five kmod package identities use their pinned normal `6.12.116-r1` release. Provider versions and architectures are frozen from pinned recipes plus retained exact-pin package evidence (`luci-base` is `x86_64`; `ucode-mod-socket` is `2026.07.09~b885dd0f-r3` in the `base` feed). The run retains matching candidate IPKs before checking control identity, so a failed identity remains reviewable. The normal Dockerman target, not a manual provider command, must produce Go host 1.26.11; the runner checks its version only after the app target succeeds. The selected app version is also recomputed from pinned `luci.mk` `findrev` inputs (excluding `po`) and must equal `26.134.50559~d5129a1`.

The standard order is tools, toolchain, `target/linux/compile`, `package/kernel/linux/compile`, then `package/feeds/luci/luci-app-dockerman/compile`, each through normal `make -j2 ... V=s`. The run does not use `NO_DEPS` or manually compile providers. The ordinary app graph includes Docker, dockerd, Compose, ttyd, Go host and kernel dependencies. The retained metadata graph has 54 target identities, 149 emitted edge records, four unresolved predicates, one unsupported compound condition, and seven targets with no positive row; it is useful input evidence but not a complete Make closure proof.

The reviewed selected-scope graph projection contains six directed circular edges: dockerd→containerd, containerd→dockerd, dockerd→tini, tini→dockerd, containerd→runc and runc→dockerd. The runner records exact GNU Make `Circular ... dependency dropped.` warning lines from the build and ignores ordinary source paths such as `vendor/.../circular.go`. It accepts only warnings that parse to those six directed edges; it does not predict which edge Make drops, how many warnings appear, or claim that cycles are resolved. A malformed GNU Make cycle line or an unknown edge is a failure. Provider presence and the selected app byte comparison remain required regardless of warnings.

The pinned config also selects two hidden display helpers globally. The exact observed metadata package config and the kernel modules `video.mk` source explain the warnings `kmod-drm-exec is not available in the kernel config - generating empty package` and `kmod-drm-suballoc-helper is not available in the kernel config - generating empty package` when their `CONFIG_DRM_EXEC` and `CONFIG_DRM_SUBALLOC_HELPER` objects are disabled. During kernel-package compilation, the candidate retains exactly one copy of each exact warning on stderr under the exact profile digest. If the same pair recurs during `dockerman-compile`, the runner accepts it only after checking the exact prior kernel warning receipt, pinned config, retained/live kernel `.config` and `.vermagic`, kernel IPK inventory, and `kernel_evidence.recheck()`. Before interpreting phase diagnostics, it snapshots provider IPKs, prepared files, the full stage including `CONTROL`, and the app IPK. It reopens the retained provider manifest and physical files and compares them with live paths before package comparison. All other empty-package or missing-module diagnostics fail. These packages are global display selections and are not direct dependencies declared by the Dockerman recipe. This narrow diagnostic disposition does not establish complete kernel module coverage or waive a failure in any required Dockerman provider. The independent kernel inventory and kernel IPK validator must still pass. This is a narrowly scoped warning disposition for two globally selected display helpers, not a waiver for other missing modules.

Moby `docker-v29.6.1` is pinned to peeled commit `8ec5ab355a34b2a0e2b3238d67bdefe77fefa982`; Docker CLI `v29.6.1` is pinned to `8900f1d330cb39e93e16d780a26bff1d7e07ba03`. The runner checks both tag objects and peeled commits with `git ls-remote`, then leaves the pinned recipe's normal shallow tag checks and source hash checks intact. It never bypasses these network checks. Go 1.26.11 is built as an ordinary dependency. An Ubuntu 24.04 x86_64 host needs at least 15 GiB RAM, 60 GiB free disk and two CPUs; the workflow has a 360-minute cap. The five Make phases have 30, 45, 45, 25 and 175 minute timeouts respectively, leaving 40 minutes in the job limit for source retrieval, metadata setup and cleanup. The first full attempt, run [45791493563](https://github.com/lucas-albers-lz4/codeql-openwrt/actions/runs/45791493563), reached the normal Dockerman target and returned exit 0 after 1,001.84 seconds (16m42s). It retained app IPK candidate SHA-256 `16cc2dd37767f51be361a9b787d1c85fe83ab040c54394b5145a02caed92292d`, but the wrapper failed before prepared/stage/IPK comparison because it rejected a repeated exact DRM warning pair and misread a vendored `circular.go` path as a Make cycle. The run artifact is [15107816620](https://github.com/lucas-albers-lz4/codeql-openwrt/actions/runs/45791493563/artifacts/15107816620). This elapsed interval includes normal dependency work scheduled by the Dockerman target; it does not isolate Go/bootstrap or kernel costs and is not the full workflow duration. A 2–6 hour total remains a planning estimate; timeout or resource stop remains a failed, retained attempt. The safe streamed artifact packer retains output only when it is within a 2 GiB cap and rechecks each file digest while streaming it into the archive.

The workflow has offline PR checks and a separate manual build job gated on those checks. The first manual attempt is a retained failure, not a successful comparison: its main IPK bytes were captured, but prepared/stage/source comparison and provider finalization did not run. The postguard changes described above have not been run against a new build. No image build, runtime test or security coverage claim is included.
